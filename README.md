# Voyager Compiler

The Voyager Compiler maps PyTorch models onto DNN accelerators generated by
[Voyager](https://arxiv.org/abs/2509.15205). It captures a static graph with
[PyTorch 2 Export](https://docs.pytorch.org/docs/stable/export.html),
quantizes it with
[PT2E quantization](https://docs.pytorch.org/ao/stable/tutorials_source/pt2e_quant_qat.html),
and lowers it through operator fusion, tiling, memory planning and scheduling to
a hardware IR serialized as a [Protocol Buffer](https://protobuf.dev/). A C
backend turns that IR into the accelerator's instruction bitstream.

The model stays an executable PyTorch FX graph at every stage, so each step of
the lowering can be checked numerically against the original model.

![Voyager overview](figures/overview.png)

## Features

- **Quantization data types.** Integers of any width, minifloats (FP8, FP4 and
  custom `fp<B>_e<X>m<Y>`), posits, and lookup-table codebooks seeded with
  NormalFloat levels (e.g. NF4).
  They can be per-tensor, per-channel, microscaling (MX, NVFP4) or group-wise.
  Precision can be mixed per module or per operator.
- **Quantization research tools.** Codebook fitting, GPTQ, outlier
  filtering with sparse outlier matmuls, a KIVI-style 2-bit KV cache,
  stochastic rounding, and quantized training (QAT or quantized forward and
  backward passes).
- **Hardware-aware lowering.** Padding to the PE array, data-layout
  normalization, and fusion of vector ops into matrix ops. Each operator's tile
  is chosen by an analytical cost model. The search explores loop nests with
  the bundled [`interstellar`](src/interstellar) mapper. Layers are rewritten
  into explicit loop nests with software pipelining (double buffering), and
  DRAM and the on-chip scratchpad are planned.
- **Performance estimation.** An analytical latency and DRAM-traffic report
  for the compiled program: an Excel workbook plus a
  [Perfetto](https://ui.perfetto.dev) trace. A design-space sweep driver for
  Llama models is included.
- **AWS Trainium backend.** It runs Voyager's own schedule on a Trainium
  NeuronCore by translating the IR to NKI kernels (see
  [its README](src/voyager_compiler/backend/trainium/README.md)).

## Installation

Python 3.10 or newer. The pinned PyTorch stack (`torch==2.12.1`,
`torchao==0.17.0`, `transformers==5.13.0`) is required. Install it with:

```bash
git clone https://github.com/jeffreyyu0602/voyager-compiler-2.git
cd voyager-compiler-2
pip install -e .            # or: pip install -e ".[dev]" for black and ruff
```

You also need:

- **Graphviz:** the `dot` binary from your system package manager. The
  compiler uses it to render the compute graph.
- **A Hugging Face login** (`hf auth login`) for the model and dataset
  downloads. The Llama models (`meta-llama/Llama-3.1-8B`) are gated, and so is
  the ImageNet set the CNNs and ViT calibrate on (`timm/imagenet-1k-wds`).
  Accept their terms on the Hub first.

Compilation runs on the CPU, and no accelerator is needed.

## Quick start

`scripts/compile_model.py` is the end-to-end driver. It loads a model, quantizes
and calibrates it, runs the lowering, and writes the compiled program. This
command compiles ResNet-18 with FP8 (E4M3) for a 16×16 PE array:

```bash
python scripts/compile_model.py resnet18 \
    --activation fp8_e4m3 --weight fp8_e4m3 --bf16 \
    --tensor_layout nhwc --gemm_layout 'xc,ck->xk' --pe_array_size 16,16 \
    --scratchpad_size 2097152 --scratchpad_banks 16 --scratchpad_word_bytes 16 \
    --model_output_dir out/resnet18 --debug
```

It writes:

| File | Contents |
|---|---|
| `model.txt` | The compiled program: the `voyager` IR as a text-format protobuf |
| `layers.txt` | A table of the compiled layers |
| `resnet18.svg` | The compute graph |
| `tensor_files/` | Every tensor's values (only with `--dump_tensors`) |

`--debug` re-runs the transformed graph (for `clm` and `--training`, the
compiled one) and compares its output with the quantized model's
(`Results match (max deviation …)`). A mismatch prints a warning. Without the
flag the check is skipped.

### Models

The driver's first argument picks the model:

| Name | Model |
|---|---|
| any `torchvision.models` name (`resnet18`, `resnet50`, `mobilenet_v2`, …) | ImageNet CNNs |
| `bert`, `mobilebert` | BERT-base and MobileBERT on GLUE (`--task_name`, default `sst2`) |
| `vit` | ViT-B/16 (`google/vit-base-patch16-224`) |
| `clm` | A causal LM (default Llama-3.1-8B): the one stage `--stage` names, `prefill`, `decode` or `training` |

`--model_name_or_path` loads a different checkpoint. `--num_hidden_layers N`
compiles only the first `N` layers of BERT, MobileBERT or a causal LM.
`--context_length` sets the causal LM's prompt length. A prefill step processes
that many tokens, and a decode step starts with that many already in the KV
cache. A decode stage takes `--kv_cache kivi` for a KIVI 2-bit KV cache
(with `--residual_length`), and `--decode_tokens N` for a speculative-decoding
verification step over `N` draft tokens.

`--stage training` (`clm`) and `--training` (`bert`) compile one full training
step instead: a gradient program and an AdamW update program, written to
`gradient/` and `update/` under the output directory. Quantized training also
needs `--error` (the gradient spec).

### Known-good configurations

These are the schemes the regression suite (`test/run_ci.py`) compiles on
every change:

| Scheme | Flags |
|---|---|
| FP8 E4M3 | `--activation fp8_e4m3 --weight fp8_e4m3 --bf16` |
| Posit8 | `--activation posit8_1 --weight posit8_1 --bf16` |
| INT8 | `--activation int8,qs=per_tensor_symmetric --weight int8,qs=per_tensor_symmetric --bias int24 --calibration_steps 3 --bf16` |
| MXINT8 | `--activation int8,qs=microscaling,bs=16,pot=1 --weight int8,qs=microscaling,bs=16,pot=1 --bf16` |
| MXNF4 | `--activation lut4_to_int6,qs=microscaling,bs=64,scale=fp8_e5m3 --weight lut4_to_int6,qs=microscaling,bs=64,scale=fp8_e5m3 --residual fp8_e4m3 --quantize_fc --conv2d_im2col --bf16` |

All of them add `--tensor_layout nhwc --gemm_layout 'xc,ck->xk'
--scratchpad_size 2097152 --scratchpad_banks 16`. They also set `--scratchpad_word_bytes` to the
PE array's column count times the activation width in bytes: one byte for the
8-bit schemes, half a byte for MXNF4. To see every command in full, run
`python test/run_ci.py --list`. For example, one Llama-3.1-8B decoder layer
with MXNF4 on a 64×64 array:

```bash
python scripts/compile_model.py clm --stage prefill \
    --activation lut4_to_int6,qs=microscaling,bs=64,scale=fp8_e5m3 \
    --weight lut4_to_int6,qs=microscaling,bs=64,scale=fp8_e5m3 \
    --bf16 --tensor_layout nhwc --gemm_layout 'xc,ck->xk' --pe_array_size 64,64 \
    --scratchpad_size 2097152 --scratchpad_banks 16 --scratchpad_word_bytes 32 \
    --context_length 1024 --num_hidden_layers 1 \
    --quantize_attention_mask --remove_fp32_casts \
    --model_output_dir out/llama_prefill
```

## Quantization specs

Each operand's data type is a comma-separated spec string. The first field
is the data type, and the rest are `key=value` options:

```
int8,qs=microscaling,bs=16,ax=-1,scale=fp8_e5m3
```

| Data type | Example | Meaning |
|---|---|---|
| `int<N>`, `uint<N>` | `int8`, `uint4` | Integers |
| `fp<B>_e<X>m<Y>` | `fp8_e4m3`, `fp4_e2m1` | Minifloats. `fp8_e4m3` saturates at 448, and the `_ieee` variant (`fp8_e4m3_ieee`) at 240 |
| `posit<N>_<es>` | `posit8_1` | Posits |
| `lut<I>_to_<E>` | `lut4_to_int6` | `I`-bit indices into a table of `2^I` entries of type `E`, seeded with NormalFloat levels |

| Key | Option |
|---|---|
| `qs` | Scheme: `per_tensor_symmetric`, `per_channel_symmetric`, `microscaling`, `group_wise_affine`. Without `qs`, the value is cast straight to the type with no scale |
| `bs` | Block size (microscaling and group-wise) |
| `ax` | Channel or block axis |
| `scale` | Block-scale data type for microscaling and group-wise, such as `fp8_e5m3` |
| `pot` | Power-of-two scales (`pot=1`) |
| `gs` | NVFP4-style global scale (`gs=1`): microscaling with a `scale` type and no `pot` |
| `sr` | Stochastic rounding (microscaling only) |
| `qmin`, `qmax` | The code range the scale maps the observed maximum onto (default: the type's range). `qmin` is used by `group_wise_affine` only |
| `ahl` | Amax history length |
| `othr`, `opct` | Outlier threshold or percentile (set one): outliers are kept in a sparse side matrix. Microscaling GEMM inputs only |

The flags are `--activation`, `--weight`, `--bias` and, for training,
`--error` (gradients). For the torchvision CNNs, `--residual <dtype>` also
quantizes the residual adds, per tensor.

For mixed precision, the Llama models take `--qconfig <name>`: a named table
from
[`quantization_configs.py`](examples/language_modeling/quantization_configs.py),
keyed by module name, module type or op. In Python, use the quantizer's
`set_module_name` / `set_object_type` methods.

## Python API

The driver is a thin wrapper around this flow:

```python
import torch

import voyager_compiler as vc

torch.set_grad_enabled(False)

model = torch.nn.Sequential(
    torch.nn.Linear(256, 512),
    torch.nn.ReLU(),
    torch.nn.Linear(512, 256),
).bfloat16()
example_args = (torch.randn(1, 128, 256, dtype=torch.bfloat16),)

# 1. Quantize with PT2E: MXINT8 activations and weights.
mxint8 = "int8,qs=microscaling,bs=16,pot=1"
quantizer = vc.get_default_quantizer(input_activation=mxint8, weight=mxint8)
gm = vc.prepare_pt2e(model, quantizer, example_args)
gm(*example_args)  # calibration
gm = vc.convert_pt2e(gm)
reference = gm(*example_args)

# 2. Lower to a 16x16 array with a 2 MB, 16-bank scratchpad.
config = vc.AcceleratorConfig(
    pe_array_size=(16, 16),
    scratchpad_size=2 * 1024 * 1024,
    num_banks=16,
    scratchpad_word_bytes=16,
)
vc.transform(
    gm,
    example_args,
    config=config,
    tensor_layout="nhwc",
    gemm_layout="xc,ck->xk",
)
vc.compile(gm, example_args, config=config, output_dir="out")

# 3. The lowered graph still runs and matches the quantized model.
torch.testing.assert_close(gm(*example_args), reference)
```

- **`transform()`** runs the graph-level passes in place. They fold
  quantize/dequantize into their producers, pad matrix and vector ops to the
  hardware, normalize data layouts, and fuse operators. Pass `patterns` to
  choose which op chains fuse; `FUSION_PATTERNS` in `scripts/compile_model.py`
  is the tested set.
- **`compile()`** tiles each operator, rewrites it into explicit loop nests,
  plans memory and emits the IR. It returns the IR's `Model` proto and writes
  `model.txt`, `layers.txt` and `compute_graph.svg` (renamed with
  `output_file`) to `output_dir`. It also dumps every tensor to
  `tensor_files/` unless you pass `dump_tensors=False`.

Keep gradients off while lowering: the lowered kernels update their buffers
in place.

`AcceleratorConfig` describes the target: a weight-stationary systolic array
plus a vector unit, input, weight and accumulation buffers, a banked
scratchpad, and DRAM. On the command line the same fields are flags:
`--pe_array_size`, `--vector_unit_width`, `--scratchpad_size`, `--scratchpad_banks`,
`--scratchpad_word_bytes`, `--dram_bandwidth`, `--frequency`, and so on (see
`python scripts/compile_model.py --help`). The tile search needs
`scratchpad_size` and `num_banks`. Double buffering is on by default; turn it
off with `--no-double_buffered_l2`.

## The `voyager` IR

The schema is [`voyager_ir.proto`](src/voyager_compiler/codegen/voyager_ir.proto).
A `Model` lists its inputs, parameters and outputs as `TensorBox`es with
memory addresses, plus a sequence of `Operation`s. Each operation is a
primitive op, a fused op, a loop, a condition or an async region. Storage (a
`TensorBox`) is allocated once. Each use is a `TensorBoxRef` that repeats the
box and adds the window it reads. Compute writes into a named destination, and
DMA transfers synchronize through semaphores. Loops, conditions and index
arithmetic run on the control processor; the index arithmetic is emitted as
primitive ops tagged `op: "cpu"`.

The generated `voyager_ir_pb2.py` is checked in. After editing the schema,
regenerate it with `bash src/voyager_compiler/codegen/compile_protos.sh`
(needs `protoc`).

## Performance estimation

Add `--report` to a `compile_model.py` run to estimate the compiled program's
latency and DRAM traffic. It writes `schedule.xlsx` (per-operation breakdown)
and `schedule.perfetto.json` (a timeline with Matrix, Vector, DRAM and
Control tracks; open it at [ui.perfetto.dev](https://ui.perfetto.dev)) to the
output directory.

`benchmarks/runner.py` sweeps LLM design points with this estimator, starting
from a Llama-3.1-8B baseline: context length, model size, quantization, model
family (Llama, Mistral, Qwen, Gemma), PE array size, scratchpad size and DRAM
bandwidth, each for prefill and decode. It writes a
workbook with charts and a `provenance.txt` naming the code that produced it:

```bash
python benchmarks/runner.py --only quant --jobs 4
```

## AWS Trainium

The Trainium backend reuses Voyager's tiling, bufferization and memory
planning with a Trainium cost model. It then translates `model.txt` into NKI
kernels and a host program:

```bash
python benchmarks/trainium/compile_lm.py \
    --model meta-llama/Llama-3.1-8B-Instruct --phase prefill \
    --context 1024 --layers 1 --target trn2 --dtype bf16 --out out/trn
```

Checking the kernels in the NKI simulator, tracing and timing on a device
need the AWS Neuron SDK (neuronx-cc, NKI and NxD Inference) in a separate
environment. The
[Trainium README](src/voyager_compiler/backend/trainium/README.md) lists the
scripts for those steps and what is not supported yet.

## Regression testing

`test/run_ci.py` compiles a fixed set of model, scheme and PE-array
combinations covering the schemes above (`--list` prints them), once with the
baseline (the origin/main commit your branch started from, or `--base`) and
once with your checkout, uncommitted edits included. It compares each
`model.txt` after `tools/canon_model.py` renames its FX-numbered values, and
the predicted latency and DRAM bytes. Every build runs the numeric check
(`--debug`); when both builds of a config fail it, the outputs they print are
compared too. A change shows up as a `MISMATCH`, with the local commit that
caused it and a drafted change-log entry; `CHANGELOG.md` records what each
commit changed. Builds are cached by source, so a rerun compiles only what
changed:

```bash
python test/run_ci.py ci_runs                   # full suite
python test/run_ci.py ci_runs --only resnet18   # a subset
```

It exits non-zero only when your code fails to compile a command, or when
another run is using the same output folder.

## Development workflow

Before every push, rebase on origin/main and then, in this order:

1. **Every test under `test/` passes**, the slow ones included:

   ```bash
   python -m pytest test --run-slow
   ```

2. **The CI passes completely.** A full run must end with `RESULT: PASS`:
   every config compiles with your code. A full run takes about 75 minutes,
   so pass `--jobs` and `--threads` to fit the cores you have.

   ```bash
   python test/run_ci.py ci_runs --jobs 6 --threads 4
   ```

3. **Every change is attributed and recorded in `CHANGELOG.md`.** Each
   `MISMATCH` or `NEW` config in `ci_runs/<time>/report.txt` names the
   commit that caused it. Every such commit gets an entry in `CHANGELOG.md`
   that says what changed in `model.txt`, in predicted latency and DRAM
   traffic, and in the numerics (whether the printed outputs changed), and
   why. Start from the run's `changelog_draft.md` and write each reason
   from the code. A change you cannot explain is a bug to fix, not an
   entry.

4. **Commit the change log last.** Entries name commits by hash, so write
   them after the final rebase, and commit `CHANGELOG.md` on top of the
   commits it describes.
